# 签名与密钥

## 机制

- 清单 `manifest.json` 用 **usign（ed25519）** 签名，生成独立的 `manifest.json.sig`；
- 应用侧用固件内自带的 `/usr/bin/usign` 验签，公钥随应用安装在 `/etc/fwupgrade/pubkey.oc-2026`；
- `require_signature=1` 时，清单没有签名或签名无效 → 直接拒绝（退出码 6）；`=0` 时「有签名必须验、无签名放行但记日志」。

## 已发布

| 项 | 值 |
|---|---|
| key id | `oc-2026`（usign 注释 `onecloud-upgrade-2026`） |
| 公钥 | `package/fwupgrade-core/files/etc/fwupgrade/pubkey.oc-2026` |
| 私钥 | **不在仓库**，存放于仓库外的 `keys-onecloud-upgrade/onecloud-upgrade-2026.key`（仅发布者持有） |
| 已签名对象 | 固件 Release `OneCloud_openwrt-25.12_26.11.18_16.27.30` 的 `manifest.json` + `manifest.json.sig` |

## 发布者怎么签

```sh
# 1) 生成清单（按 Release 资产填 sha256/大小/target）
python3 tools/gen_manifest.py --repo 2286927/onecloud-25.12-onlineFirmware -o manifest.json

# 2) 签名（需要 usign；Windows 可在设备或任意 OpenWrt/Linux 上执行）
usign -S -m manifest.json -s onecloud-upgrade-2026.key -x manifest.json.sig

# 3) 两个文件一起作为 Release 资产上传
```

应用侧校验：

```sh
usign -V -p /etc/fwupgrade/pubkey.oc-2026 -x manifest.json.sig -m manifest.json
```

## 密钥轮换

1. 生成新密钥（注释里带年份，如 `onecloud-upgrade-2027`）；
2. 新公钥以 `pubkey.<新key_id>` 随**下一个应用版本**发布（应用会取 `/etc/fwupgrade/pubkey.*` 的第一个）；
3. 旧清单继续用旧私钥签，等设备普遍升级后再切换签名私钥；
4. **先发公钥、后发签名**——顺序反了会让旧设备验签失败。

## 边界

- 只保护「清单 + 资产 sha256」这一层信任；资产本身仍由清单里的 sha256 约束。
- 不防「设备已被 root 控制」——那时攻击者可以直接改公钥文件。
- 私钥一旦泄露，立刻按上面的轮换流程换 key，并在 Release 说明里写清楚。
