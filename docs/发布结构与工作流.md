# 发布结构与 Actions 配置

本应用不规定你用什么方式构建固件，只要求**发布出来的 Release 符合下面两种结构之一**。照着做，应用就能检测、校验并升级；不符合，`check` 会给出明确的拒绝原因，不会静默继续。

## 一、应用怎么挑 Release

`provider=github-release` 时按配置决定取哪一个：

| 配置 | 走哪个接口 | 取到什么 |
|---|---|---|
| `tag` 有值（推荐用于一仓多机型） | `GET /repos/<repo>/releases/tags/<tag>` | 精确命中，不受其他机型影响 |
| `channel=stable`、`tag` 为空 | `GET /repos/<repo>/releases/latest` | 该仓最新**正式版**（GitHub 语义：不含 draft，也不含 prerelease） |
| `channel=beta`、`tag` 为空 | `GET /repos/<repo>/releases?per_page=5` | 列表里第一个非 draft（**包含** prerelease） |

由此有两条容易踩的规则：

- Release 勾了 **prerelease** → `stable` 永远看不到它，要么用 `channel=beta`，要么用 `tag`。
- Release 存成 **draft** → 谁都看不到。

版本号从 tag 里抽：能匹配到 `YY.MM.DD_HH.MM.SS`（如 `OneCloud_openwrt-25.12_26.11.21_08.59.21` → `26.11.21_08.59.21`）就按它比；抽不到就把整个 tag 当版本串比，容易误判。**建议 tag 里带上这个时间戳**。

## 二、两种发布结构

### 结构 A：带 manifest（推荐）

同一 Release 下四个资产：

```
<tag>/
├── immortalwrt-amlogic-meson8b-thunder-onecloud-rootfs.tar.gz   ← rootfs 包
├── onecloud-boot.tar.gz                                          ← boot 包
├── manifest.json                                                 ← 清单（权威）
└── manifest.json.sig                                             ← usign 签名（可选但建议）
```

有了 `manifest.json`，应用以它为准：版本、`target`/`compatible`（机型校验）、`flasher.abi`、每个资产的 `size`/`sha256` 全部来自清单，不再依赖资产名与 digest。

### 结构 B：不带 manifest（兼容模式，零改动）

只放两个资产，名字与配置里的 `asset_rootfs` / `asset_boot` **完全一致**：

```
<tag>/
├── immortalwrt-amlogic-meson8b-thunder-onecloud-rootfs.tar.gz
└── onecloud-boot.tar.gz
```

应用会自己合成清单：版本从 tag 推、`sha256` 取 GitHub 为资产计算的 **digest**、`target` 留空（跳过机型校验）、不走签名。

代价很明确：**没有机型校验**（换错设备的包也会被放行，靠设备脚本自己的版本核对兜底）、**没有签名**。用来快速接入可以，长期建议升到结构 A。

### 两种结构都必须满足

| 要求 | 说明 | 不满足时 |
|---|---|---|
| rootfs 与 boot **两个角色齐全** | 名字对上配置项即可 | `rc=6`「release 里找不到资产：xxx」 |
| 资产有 `sha256` digest | GitHub 为每个上传的资产自动算；API 里字段是 `digest` | `rc=6`「缺少 sha256 digest，拒绝继续」 |
| 资产 `size > 0` | 空文件视为异常 | `rc=6` |
| `manifest.json` 的 `schema` 为 1 | 高版本清单会被拒绝 | `rc=6`「清单 schema=N 不受支持」 |
| 签名（若存在）必须验过 | 有 `.sig` 就一定校验 | `rc=6`「清单签名校验失败」 |

默认值（都可在页面改）：

```
repo         = 2286927/onecloud-25.12-onlineFirmware   # 官方仓，开箱可用
asset_rootfs = immortalwrt-amlogic-meson8b-thunder-onecloud-rootfs.tar.gz
asset_boot   = onecloud-boot.tar.gz
tag          = （空 = 走 stable/latest）
```

> 上面提到的 `targz-rootfs.tar.gz` 是同一份内容的另一种打包方式，应用默认选 `rootfs.tar.gz`，别两个都当 `asset_rootfs`。

## 三、一仓多机型怎么办

`ImmortalWrt-MultiDevice` 这类仓是「一个机型一个 Release tag」，`/releases/latest` 指向最后发布的那个机型，跟你的设备无关。两种解法：

1. **填 `tag`**（本次实测采用）：页面上把「指定 tag」填成 `OneCloud_openwrt-25.12_26.11.21_08.59.21`。
2. 每个机型一个仓，各自 `latest` 干净。

填了 `tag` 之后 `channel` 不生效（tag 优先）。

## 四、GitHub Actions 怎么配

下面是固件仓最小可用的发布流水线，产出结构 A（不含签名时即结构 B）。

```yaml
name: firmware-release
on:
  push:
    tags: ['*']
  workflow_dispatch:

permissions:
  contents: write          # 创建 Release + 上传资产需要

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 构建并收集产物
        run: |
          mkdir -p out
          # ……你的构建步骤……
          # 必须产出这两个文件（名字可自定，但要与设备上配置的 asset_rootfs/asset_boot 一致）
          ls -l out/
          test -f out/immortalwrt-amlogic-meson8b-thunder-onecloud-rootfs.tar.gz
          test -f out/onecloud-boot.tar.gz

      - name: 创建 Release 并上传固件资产
        uses: softprops/action-gh-release@v2
        with:
          files: |
            out/immortalwrt-amlogic-meson8b-thunder-onecloud-rootfs.tar.gz
            out/onecloud-boot.tar.gz
          draft: false
          # 想走 beta 通道就设 true（stable 将看不到）；正式发布设 false
          prerelease: false
          fail_on_unmatched_files: true

      # 下面两步只有在要做结构 A（带清单）时才需要
      - name: 生成 manifest（必须在上传资产之后）
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          python3 tools/gen_manifest.py \
            --repo "${{ github.repository }}" \
            --release "${{ github.ref_name }}" \
            --target amlogic/meson8b \
            --compatible thunder,onecloud \
            -o manifest.json
          cat manifest.json

      - name: 签名清单（有私钥才执行）
        if: env.USIGN_KEY != ''
        env:
          USIGN_KEY: ${{ secrets.USIGN_KEY }}
        run: |
          sudo apt-get update -qq && sudo apt-get install -y -qq build-essential cmake libssl-dev git
          git clone -q https://git.openwrt.org/project/usign.git /tmp/usign
          cmake -S /tmp/usign -B /tmp/usign/build >/dev/null && cmake --build /tmp/usign/build >/dev/null
          printf '%s' "$USIGN_KEY" > /tmp/key && chmod 600 /tmp/key
          /tmp/usign/build/usign -S -s /tmp/key -m manifest.json -x manifest.json.sig
          rm -f /tmp/key

      - name: 上传清单与签名
        uses: softprops/action-gh-release@v2
        with:
          files: |
            manifest.json
            manifest.json.sig
          fail_on_unmatched_files: false
```

### 四个必须知道的细节

1. **manifest 一定要在资产上传之后生成**。`gen_manifest.py` 是通过 Release API 读每个资产的 `digest` 来填 `sha256` 的；先传清单再传固件，清单里的哈希就是错的（应用会在校验阶段直接拒绝）。
2. **资产名不要在 workflow 里改**。应用默认按固定名字找资产（结构 A 里则由清单的 `url` 决定，但结构 B 完全依赖名字）；改名要么同步改设备配置，要么走结构 A。
3. **`prerelease` 会影响通道**。勾了 prerelease，`channel=stable` 的设备看不到；要发预览版就用 `channel=beta` 或显式 `tag`。
4. **签名私钥放 Secret，公钥随设备**。私钥进 `secrets.USIGN_KEY`；公钥命名为 `/etc/fwupgrade/pubkey.<名字>`（应用自动取第一个非 `.bak` 的文件）。`require_signature=1` 时，清单缺 `.sig` 会直接拒绝升级。

## 五、别和本仓的 CI 搞混

本仓（`luci-app-onecloud-upgrade`）的 `.github/workflows/build-packages.yml` 只做一件事：用 OpenWrt SDK 编出 5 个 apk 并附到本仓 Release。它**不产出固件**，与上面的「固件发布结构」是两回事。

## 六、发布完怎么自检

在设备上：

```sh
/usr/libexec/fwupgrade/fwupgradectl check     # 最后一行就是 JSON：identity / available / assets
/usr/libexec/fwupgrade/fwupgradectl config    # 确认 repo / tag / 资产名 / 签名开关
```

`identity` 三种取值：

| 值 | 含义 |
|---|---|
| `target_ok+compatible_ok` | 清单声明了 `target` 且设备树兼容（结构 A 的理想结果） |
| `target_ok` | 清单只声明了 `target`，没写 `compatible` |
| `no_target_in_manifest` | 兼容模式（结构 B），机型未校验 |

常见拒绝原因对照：

| 现象 | 原因 |
|---|---|
| `release 里找不到资产：xxx` | 资产名与配置不一致，或 `latest` 取到了别的机型的 Release（该用 `tag`） |
| `资产 xxx 缺少 sha256 digest` | 资产不是通过 Release 上传的（或平台没给 digest） |
| `目标平台不符：清单=… 本机=…` | 结构 A 清单里的 `target` 与设备 `DISTRIB_TARGET` 不同 |
| `设备树不匹配：清单=… 本机=…` | 清单 `compatible` 与本机 `/proc/device-tree/compatible` 无交集 |
| `清单签名校验失败` | 私钥换过、清单被改，或工作目录里残留了上一轮的旧 `.sig`（v0.1.1 起已自动清理） |
| `设备脚本判定已是最新、未写入` | 应用的清单地址没传给设备脚本（v0.1.1 起改用 `--url` + `OC_REPO`，正常不会出现） |
