## 0. 结论

**不具备公开发布到 GitHub 的条件；具备「私有仓库 + 单机内测」的条件。**

理由三条：

1. **主链路是真跑通的**：检测 → 预取 → 写入 → 重启 → 恢复判定，在现网机上完成过一次真实重刷（T4），串口无 panic，版本/配置/服务均恢复。
2. **但发布形态不成立**：没有 LICENSE、没有 `.gitignore`、没有 git 历史；打包依赖缺项（缺 provider 包）；界面没有国际化；工具里硬编码了设备 IP；`evidence/` 里有内网信息。这些不是"以后再补"，是"公开即事故/公开即被拒"的级别。
3. **关键路径仍有未验证面**：故障注入 0/24 执行、并发与掉电未测、同版本重刷的成功判据存在逻辑漏洞、安装包从未真正构建过。

建议路径：**私有仓库 v0.1.0-alpha（内测）→ 补 P0 → v0.1.0-rc（小范围）→ 公开**。

## 3. 已知缺陷

### P0（发布阻断）

| # | 缺陷 | 位置 | 影响 |
|:-:|---|---|---|
| P0-1 | **luci-app 依赖漏了 provider 包** | `package/luci-app-onecloud-upgrade/Makefile:10` | 从 feed 安装后 `check` 直接报"provider 脚本不存在"，应用开箱即坏 |
| P0-2 | **同版本重刷的成功判据是"版本相等"** | `fwupgradectl:224` | force 重刷时版本本来就相等：即使写入失败、设备重启回旧系统，也会被判 `ok`。T4 的真实成功是靠脚本自身记录佐证，应用没能力分辨 |
| P0-3 | **evidence 与设备信息会随仓库公开** | `evidence/`（串口日志含内网 IPv6/MAC）、`tools/*.py:15/17/19`（默认 `192.168.1.43`） | 内网拓扑、MAC、主机名外泄 |
| P0-4 | **无 LICENSE / .gitignore / git 历史** | 仓库根 | 无许可证 = 默认保留所有权利，别人不能用；无历史无法追溯 |
| P0-5 | **安装包从未构建** | 全部 Makefile | `luci.mk` 路径、依赖语法、apk 打包均未验证，"能装"目前只是手工拷贝 |

### P1（首版体验/正确性）

| # | 缺陷 | 位置 | 影响 |
|:-:|---|---|---|
| P1-1 | UI 无法切换 `dry_run` / `force` | rpcd `config_set` 白名单只到 `channel` | 用户装完只能看不能升，必须 SSH 改 UCI；与"给买家用的图形界面"目标冲突 |
| P1-2 | 无阶段进度 | `progress` 恒 0 | 197 s 写入期间只有一句"正在写入"，用户无法判断卡住还是正常 |
| P1-3 | `clean` 不清 diag/备份/回滚快照 | `fwupgradectl:424` | 长期使用会累积；`/opt` 与 docker 共享分区 |
| P1-4 | 无 `jsonfilter` 显式依赖 | core Makefile `DEPENDS` | 设备刚好有；精简固件上 rpcd 方法会静默失败 |
| P1-5 | `apply` 依赖 `setsid`，无兜底 | `fwupgradectl:212` | 若 setsid 缺失，worker 不启动，状态永久停在 `applying` |
| P1-6 | 非 root 用户默认只有 read | 无 uci-defaults 分配 ACL 组 | 多用户设备上"能看不能升"，且没有说明 |
| P1-7 | 回滚不预检 network/firewall | `cmd_rollback` | 一键恢复旧配置可能直接切断当前连接（UI 有文字警告，但无阻断） |
| P1-8 | 界面未标注"未启用签名校验" | `overview.js` | 与设计承诺不一致，用户会误以为有真实性校验 |

### P2（整洁度）

- `backups` 表格里现网备份"时间"列显示 `20261106T214950` 原始格式；
- `meta.txt` 的 `mixed` 字段在 state 缺键时为空；
- `check` 在 force 模式返回 `update_available:false` 但 phase=ready，语义别扭；
- `github.sh` 只支持 stable，beta/dev 直接报未实现（README 已写）。

## 6. 发布前必须解决（Gate）

1. 补 provider 依赖（P0-1），并在 SDK 里真的构建出 5 个包，装一遍、卸一遍。
2. 修 force 重刷判定（P0-2）：记录 apply 前 boot_id，恢复时要求 boot_id 变化 + 脚本 last record 为 `reboot-ok`；两者缺一即 `unknown`。
3. 仓库卫生（P0-3/4）：`git init` + `.gitignore`（evidence/、.ssh-ops/、__pycache__、*.log）+ LICENSE + 把设备 IP 改成必填环境变量。
4. 补 `dry_run` 开关到 UI（P1-1），并在页面上明确"当前是演练/实盘"。
5. 加 `jsonfilter` 依赖（P1-4）与 setsid 兜底（P1-5）。
6. 至少跑 6 条关键故障注入：sha 篡改、资产 404、空间不足、重复提交、非 root 调用、回滚失败。
7. 写安装说明 + 救援指引 + 支持矩阵。
8. 加一个最小 CI：`sh -n` 全量、`tests/test_core.sh`、JSON 校验、grep 禁止硬编码 IP。

## 7. 主要风险

| 风险 | 说明 |
|---|---|
| 写 boot 不可逆 | 单机型、无 A/B；一次失败就是线刷 |
| 判据错误导致"假成功" | P0-2 是这一类；比崩溃更危险，因为用户不会去救 |
| 依赖"现网脚本"的隐式契约 | 脚本被镜像覆盖、被 cron 改写；接口语义一变，应用静默失效 |
| 单机验证偏差 | 所有证据来自一台设备；买家设备的 eMMC/分区/空间可能不同 |
| 维护面 | 5 个包 + 1 个脚本 + 1 条发布流水线，一个人维护成本不低 |
