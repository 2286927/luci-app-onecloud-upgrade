## 0. 结论

**不具备公开发布到 GitHub 的条件；具备「私有仓库 + 单机内测」的条件。**

理由三条：

1. **主链路是真跑通的**：检测 → 预取 → 写入 → 重启 → 恢复判定，在现网机上完成过一次真实重刷（T4），串口无 panic，版本/配置/服务均恢复。
2. **但发布形态不成立**：没有 LICENSE、没有 `.gitignore`、没有 git 历史；打包依赖缺项（缺 provider 包）；界面没有国际化；工具里硬编码了设备 IP；`evidence/` 里有内网信息。这些不是"以后再补"，是"公开即事故/公开即被拒"的级别。
3. **关键路径仍有未验证面**：故障注入 0/24 执行、并发与掉电未测、同版本重刷的成功判据存在逻辑漏洞、安装包从未真正构建过。

建议路径：**私有仓库 v0.1.0-alpha（内测）→ 补 P0 → v0.1.0-rc（小范围）→ 公开**。

## 3. 已知缺陷

### P0（发布阻断）

| # | 缺陷 | 位置 | 影响 |
|:-:|---|---|---|
| P0-1 | **luci-app 依赖漏了 provider 包** | `package/luci-app-onecloud-upgrade/Makefile:10` | 从 feed 安装后 `check` 直接报"provider 脚本不存在"，应用开箱即坏 |
| P0-2 | **同版本重刷的成功判据是"版本相等"** | `fwupgradectl:224` | force 重刷时版本本来就相等：即使写入失败、设备重启回旧系统，也会被判 `ok`。T4 的真实成功是靠脚本自身记录佐证，应用没能力分辨 |
| P0-3 | **evidence 与设备信息会随仓库公开** | `evidence/`（串口日志含内网 IPv6/MAC）、`tools/*.py:15/17/19`（默认 `192.168.1.43`） | 内网拓扑、MAC、主机名外泄 |
| P0-4 | **无 LICENSE / .gitignore / git 历史** | 仓库根 | 无许可证 = 默认保留所有权利，别人不能用；无历史无法追溯 |
| P0-5 | **安装包从未构建** | 全部 Makefile | `luci.mk` 路径、依赖语法、apk 打包均未验证，"能装"目前只是手工拷贝 |

### P1（首版体验/正确性）

| # | 缺陷 | 位置 | 影响 |
|:-:|---|---|---|
| P1-1 | UI 无法切换 `dry_run` / `force` | rpcd `config_set` 白名单只到 `channel` | 用户装完只能看不能升，必须 SSH 改 UCI；与"给买家用的图形界面"目标冲突 |

## 7. 主要风险

| 风险 | 说明 |
|---|---|
| 写 boot 不可逆 | 单机型、无 A/B；一次失败就是线刷 |
| 判据错误导致"假成功" | P0-2 是这一类；比崩溃更危险，因为用户不会去救 |
| 依赖"现网脚本"的隐式契约 | 脚本被镜像覆盖、被 cron 改写；接口语义一变，应用静默失效 |
| 单机验证偏差 | 所有证据来自一台设备；买家设备的 eMMC/分区/空间可能不同 |
| 维护面 | 5 个包 + 1 个脚本 + 1 条发布流水线，一个人维护成本不低 |

- **离线包：当前不可行，不是应用层能补的。** 设备脚本的 `--url` 定向模式仍会按 URL 里的 TAG 调 GitHub API 取 `sha256`（脚本 440–449 行），没有网络就拿不到期望摘要，直接 die。要真正离线，必须改 `/usr/lib/oc-upgrade.sh` 增加「本地清单 + 本地资产」通道——这属于固件脚本改动，等构建额度恢复后再做。
- **beta / dev 通道：已实现并通过实网验证。** stable 走 `/releases/latest`；beta/dev 走 `/releases` 列表取第一个非 draft。实测把通道切到 beta，清单仍经镜像下载、签名校验通过、机型校验通过；解析器对数组响应的单测也通过。

## 2026-11-26 10:52：boot 分区损坏 = 已验证（串口证据闭合，推翻上一节）

上一节的「未定论」作废。重读串口原文 `evidence/serial-version-upgrade-20261126.log`（10:34:32 那次启动），三件事全部对上：

1. **写坏确实落盘了**：U-Boot 在 `Enter USB burn` 等待超时后走 bootcmd，先 `fatload mmc 0:1` 失败（SD 卡不是启动盘），再 `fatload mmc 1:1` 同样失败——`** Unable to use mmc 1:1 for fatload **`。eMMC boot 分区上的 FAT 已被 2MB 随机数据覆盖，p1 不可读。
2. **设备确实无法引导**：紧接着 `** Invalid boot device **`，U-Boot 掉到 `m8b_onecloud#` 提示符；约 15 s 后看门狗复位，形成「复位 → 提示符 → 复位」循环。这就是「boot 写坏」的真实现场，不是"回退到出厂版本"。
3. **rootfs 变成 26.11.17 是重烧，不是回退**：设备所有者在 10:34:56 按上一轮提示（插双公头线 → 上电 → 点 Start）主动发起线刷，10:36:15 `burn_complete 3`，随后是全新工厂系统首启——`EXT4-fs (mmcblk1p2): resizing filesystem from 262144 to 1839104 blocks`、`/opt` 只剩 docker/containerd、`/etc/config` 38 个文件、`/opt/upgrade-backup-*` 消失。重烧后读回的 `uImage` 是出厂 11-11 06:45 版本，才造成"boot 文件还在"的假象。

结论：「boot 写入中断 / 写坏」= **不可引导**，单机型无 A/B、无自愈；恢复只有线刷（已实证两次），或掉到 `m8b_onecloud#` 时人工修。该条从**未验证改为已验证**：等价场景已完整走过「不可引导 → 线刷恢复 → 全新系统可用」。

### 顺带确认的引导事实（已同步进 `救援指引.md`）

| 项 | 值 |
|---|---|
| U-Boot 分区表 | bootloader 0/4MB、reserved 4/4MB、cache 8MB/0、env 8MB/4MB、resource 12MB/4MB、**boot 16MB/256MB**、**rootfs 272MB/7GB** |
| Linux 视角 | `mmcblk1p1` start=32768 size=524288（256MB，内含 16MB FAT16）；`mmcblk1p2` start=557056 size=14712832 |
| boot.scr（797 B） | `setenv bootargs ${bootargs_emmc}`（`root=/dev/mmcblk1p2 ro`）→ `fatload mmc 1 uInitrd`（缺失不影响启动）→ `fatload mmc 1 uImage` → `fatload mmc 1 dtb`，dtb 失败退到 `imgread dtb boot` |
| 引导顺序 | 每次上电先进 `Enter USB burn` 等约 3 s（`Try connect time out 1001, 1000, 789`），无工具应答才走 bootcmd：`fatload mmc 0:1` → `fatload mmc 1:1` |
| 中断窗口 | 有 `Hit Enter key to stop autoboot -- : 3 2 1 0`，3 s 内按 Enter 可进 `m8b_onecloud#` |
| 第二块设备 | `mmcblk0` = SD 卡槽（LX128 128GB），非启动盘（`fatload mmc 0:1` 恒失败），与引导无关 |

### 本轮测试方法上的教训（写死进预案）

- **双公头线插着 + 烧录工具已 Start 的情况下，任何上电都会重烧**。做「坏 boot」测试必须先拔线并关掉工具，否则观察到的永远是"重烧后的全新系统"，会把结论带偏。
- 判定「是否真的写坏」不能看重启后文件在不在（重烧即恢复），只能看**串口里 `fatload` 那一行**。

## 2026-11-26 11:05：回滚中断加固 + 实测（故障矩阵 24/24）

代码审查发现回滚路径有三个真实缺口，已修：

| 缺口 | 原行为 | 现在 |
|---|---|---|
| `--replace` 掉电 | `mv /etc/config → .pre` 之后再 `cp`，此间掉电会让**配置目录整个消失** | 先在 `config.new-<ts>` 旁路构建并逐文件校验，再两次 rename 切换；掉电最多停在「旧目录还在」或「新目录已就位」 |
| 合并回滚掉电 | `cp -a` 直接覆盖目标，掉电可能留下**截断文件** | 逐文件「写同目录临时名 → rename」，任何文件要么旧要么新 |
| 中断不可见 | 无阶段标记，`status` 仍显示上一次的 `ok`，用户以为回滚成功 | 写入前落 `phase=rollback` 标记；`status` 自动收口为 `idle / failed / mixed_state=C1`，detail 指明备份 ID 与补救方式 |

残留清理：`.fwu-tmp` 与 `config.new-*` 在下次执行时自动清掉；`config.pre-*`（快照）保留。
